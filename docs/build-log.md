# Build Log

One entry per build step: what was built, why, and how it was verified.

## Phase 1.1 — Project setup and local services
- Python 3.12 project managed with uv; package `src/voice_platform` (`platform` would shadow the Python stdlib).
- Typed settings from `.env` (`shared/config.py`); secrets are `SecretStr`; weak `APP_SECRET_KEY` rejected outside local/test.
- Structured JSON logging with a request ID on every line; password/token/key fields masked (`shared/logging.py`, `shared/request_context.py`).
- `/health/live` and `/health/ready` (PostgreSQL + Redis, 2 s timeout, 503 without internal details).
- `compose.yaml`: PostgreSQL 16 + pgvector, Redis 7.4; bound to 127.0.0.1; passwords from `.env`.
- Verified: unit + integration tests, ruff, mypy --strict, live API readiness check.

## Phase 1.2 — Core database and tenant isolation
- **Two database roles.** Migrations run as the owner (`MIGRATION_DATABASE_URL`). The API, worker and jobs connect as `voice_app`, which is not a superuser and cannot bypass row-level security. `uv run python -m voice_platform.cli db-setup` migrates and sets the app role's password.
- **Tables (migration `0001_foundation`):** `users` (global identity, citext email), `organizations` (tenant; slug, timezone, retention days), `roles`, `permissions`, `role_permissions` (seeded catalog), `memberships` (user × org × role), `audit_logs`, `outbox_events`.
- **Roles and permissions** (`tenancy/permissions.py`): OWNER, ADMIN, MANAGER, AGENT_MANAGER, ANALYST, VIEWER over 23 explicit permissions. No permission implies another (`calls.read` ≠ `calls.transcript.read`). Admin cannot delete the org or manage billing.
- **Row-level security** on `organizations`, `memberships`, `audit_logs`, `outbox_events`, forced for the table owner too. Policies read `app.org_id` / `app.user_id`, set per transaction by `tenant_transaction()` (`infrastructure/database.py`) with `set_config(..., true)` so values vanish at commit. No context = no rows.
  - A user sees the active org's members plus their own memberships in other orgs (for an org picker), never other users' memberships elsewhere.
- **Audit log is append-only:** the app role has no UPDATE/DELETE grant, and a trigger blocks changes even for the owner (only a retention job may purge, via an explicit flag).
- **Outbox:** events are written in the same transaction as the change; a dispatcher comes later.
- Verified (integration tests on a throwaway `<db>_test` database): models match migrations exactly; seeded catalog matches code; app role has no superuser/bypass; org A cannot read or write org B; no context sees nothing; context does not leak across pooled connections; audit log cannot be edited or deleted; migration downgrade → upgrade round trip.
- Note: IDs are UUIDv4 for now (docs proposed v7); can switch later without schema changes.

## Phase 1.3 — Sign-up, login and role checks
- **Endpoints** (`api/auth.py`, `api/organizations.py`):
  `POST /api/v1/auth/signup` · `login` · `logout` · `switch-organization` · `verify-email` · `password-reset/request` · `password-reset/confirm`, `GET /api/v1/auth/sessions`, `DELETE /api/v1/auth/sessions/{id}`, `GET /api/v1/me`, `GET|PATCH /api/v1/organizations/current`, `GET /api/v1/organizations/current/members`.
- **Sign-up** creates the user, their organization and an OWNER membership in one transaction, writes audit entries and an `organization.created` outbox event, signs the user in and sends a verification link.
- **Passwords** (`identity/passwords.py`): Argon2id, 12–128 characters, not the email, not repetitive; old hashes upgraded on login. Unknown emails take the same time to reject as wrong passwords, and both get the same message.
- **Sessions** (migration `0002_auth_sessions`): random 256-bit token in an `HttpOnly`, `SameSite=Lax` cookie (`Secure` outside local http); only its SHA-256 is stored. 14-day expiry, revocable, listed per user. The token is rotated when switching organization. A password reset signs the user out everywhere.
- **CSRF:** every state-changing request with a session must send `X-CSRF-Token`, an HMAC of the session token (returned at login and by `/me`, also in a readable `vp_csrf` cookie). Sign-up/login accept JSON only, which browsers cannot send cross-site without a CORS preflight.
- **Email tokens:** single-use, hashed, 48 h (verify) / 1 h (reset); only the newest reset link works. Reset requests answer identically whether or not the account exists. No email provider yet: locally the link is printed to the API console; staging/production refuse to start with that sender.
- **Rate limits** (Redis): sign-up 5/h per IP; login 50/15 min per IP and 10/15 min per email; reset 5/h per IP and 3/h per email. If Redis is down they fail open and log an error.
- **Authorization** (`api/dependencies.py`): tenant comes only from the session's active organization, re-checked against memberships on every request (a removed member loses access immediately). `require(Permission.X)` guards each endpoint and logs denials. Errors use one problem+json format (`api/errors.py`) and never echo submitted values.
- Fix found by tests: audit/outbox rows without an organization could not be inserted with `RETURNING` under row-level security; those models now set all defaults client-side.
- Verified: 49 tests (role matrix for all six roles, cross-organization switch blocked, CSRF required, session revocation, single-use tokens, reset signs out everywhere, rate limiting, audit + outbox written), ruff, mypy --strict, and a live sign-up → `/me` → PATCH-without-CSRF smoke test.
- Not yet: MFA (required for owners/admins later), invitations and role changes (next piece), a real email provider.

## Phase 1.4 — Team management and API conventions
- **Invitations** (migration `0003_invitations`, `api/members.py`): `POST /organizations/current/invitations` emails a 7-day single-use link; `GET` lists open ones; `DELETE …/{id}` revokes; `POST /api/v1/invitations/accept` joins. The token is `<org id>.<secret>` (only its hash is stored) and only the account whose email matches can accept; accepting also verifies that email. One open invitation per email per organization (partial unique index); row-level security on the table.
- **Role rules** (`tenancy/rules.py`, pure functions, tested over every role pair): only an OWNER grants OWNER or manages another OWNER; everyone else manages only lower-ranked members and grants at most their own rank; nobody changes their own role; an organization always keeps one OWNER (owner rows are locked while checking, so concurrent demotions can't both pass).
- **Members:** `GET /organizations/current/members` (paginated), `PATCH …/members/{user_id}` change role, `DELETE …/members/{user_id}` remove (or leave, for yourself). Removal clears the person's sessions from that organization at once.
- **Pagination** (`api/pagination.py`): keyset cursor on `(created_at, id)`, `limit` 1–100 (default 25), response `{data, next_cursor}`; invalid cursors give `400 invalid_cursor`.
- **Audit log API:** `GET /organizations/current/audit-logs` (needs `audit.read`), filterable by `action`. Role changes, removals and invitations are all audited.
- **HTTP hardening** (`shared/http_security.py`, `api/main.py`):
  - API-wide rate limit per signed-in session (or per IP when signed out), default 600 requests/minute, `429` + `Retry-After`; health checks are exempt.
  - Security headers on every response: `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `CSP default-src 'none'` on the API, `Cache-Control: no-store` on `/api/*`, HSTS in staging/production.
  - CORS allows only the dashboard origin(s) (`CORS_ALLOWED_ORIGINS`, default `PUBLIC_APP_URL`) with credentials and the `X-CSRF-Token` header.
- **OpenAPI:** 19 documented paths at `/docs` (disabled in production).
- Verified: 104 tests (unit rule matrix; invitation accept/wrong account/forged token/duplicate/revoke; rank-limited promotion; self-change blocked; last-owner protection; removed member loses access; paginated audit log; viewer denied audit; security headers; CORS allow/deny; API rate limit), ruff, mypy --strict, live header check.

**Phase 1 (foundation) is complete.** Not included yet, by design: MFA, SSO, API keys, a real email provider (all scheduled for later phases).

## Phase 2.1 — Agents, draft configuration, versions, publish and rollback
- **Agent configuration schema** (`agents/config_schema.py`): the platform's own, vendor-neutral model of an agent: purpose, language, greeting, personality, business info and weekly hours, voice choice, business rules, escalation (transfer number in E.164, triggers, after-hours message), safety (AI disclosure, recording notice, forbidden topics), limits (max call length, max tool calls per turn, silence re-prompts), tool grants with explicit permission scopes, knowledge bases, and an **Advanced** section (extra instructions, LLM model/temperature/max tokens, interruption and endpointing settings). Unknown fields are rejected and every field is bounded. Agents pick an LLM *tier* (`fast`, `balanced` default, `deep`), never a vendor model id; the provider layer maps tiers to model ids from server settings, so upgrading a model is a configuration change.
- **Templates** (`agents/templates.py`): data only. MVP ships *Receptionist* and *Restaurant Receptionist*; creating an agent copies the template into a draft filled with the organization's name and time zone. The restaurant template grants `reservations:read` and `reservations:create` separately (read never implies write).
- **Tables** (migration `0004_agents`, row-level security on all three): `agents`, `agent_configurations` (the editable draft, with a `revision` number), `agent_versions` (frozen snapshot + SHA-256 hash, status `testing` / `published` / `retired`). A database trigger makes a version's snapshot, number, agent and note impossible to change.
- **Lifecycle** (`agents/service.py`, `api/agents.py`):
  - `POST /api/v1/agents`, `GET /api/v1/agents` (paginated), `GET|PATCH|DELETE /api/v1/agents/{id}` (delete archives), `GET /api/v1/agent-templates`.
  - `GET|PUT /api/v1/agents/{id}/configuration` — saving requires the current `revision`; a stale save gets `409 revision_conflict` instead of overwriting someone else's edit.
  - `POST /api/v1/agents/{id}/versions` snapshots the draft as the next number (agent row locked, so numbers never collide). `GET …/versions`, `GET …/versions/{vid}`.
  - `POST …/versions/{vid}/publish` and `POST /api/v1/agents/{id}/rollback` move the agent's live pointer; the previous live version becomes `retired`. Calls already running keep the version they started with. Each publish writes an `agent.published` outbox event and an audit entry.
  - Publishing goes through a `PublishGate`; today it re-validates the snapshot, and the regression-test gate plugs in here later.
  - Permissions: `agents.read` to view, `agents.write` to create/edit/snapshot, `agents.publish` to publish or roll back.
- **Fix found by tests:** Windows has no built-in IANA time zone database, so time zone validation (agents and organization settings) rejected everything; added the `tzdata` package and a regression test.
- Verified: 126 tests (every template valid; invalid configs rejected with field-level errors; edit conflict; v1 → v2 → rollback to v1 with correct statuses; snapshot unchanged after later draft edits; trigger blocks edits even as the database owner; another organization gets 404 on every agent route; archive), ruff, mypy --strict.

## Phase 2.2 — LLM provider layer, conversation state, prompt assembly
- **LLMProvider port** (`runtime/llm.py`): provider-neutral request/response types (system blocks, messages, tool specs, tool calls/results, usage, stop reason). The runtime never sees vendor types, and tool calls are only *requests*: executing them belongs to the Tool Gateway (2.3). Errors are split into `LLMUnavailableError` (timeout, rate limit, overload: safe to retry or fall back) and `LLMRequestError` (misconfiguration).
- **Anthropic adapter** (`providers/llm/anthropic_provider.py`, official `anthropic` SDK 2.x), written against the current Messages API:
  - Agents choose a tier (`fast` / `balanced` / `deep`); the adapter maps it to a model id from `LLM_MODEL_FAST/_BALANCED/_DEEP` in `.env`, so the repo never names a vendor model and upgrades are a config change.
  - `output_config.effort` (default `low` for live calls) instead of temperature, which current models reject. The agent config's Advanced LLM settings now hold `effort`; older saved versions that still contain `temperature` load fine (it is ignored).
  - `tool_choice` is always `auto` (forcing a tool is rejected by current models).
  - The stable system layers carry `cache_control`, so repeated turns reuse the cached prefix.
  - Server-side refusal fallback (beta) is on by default; a refusal that survives it is reported as `REFUSAL` with its category.
  - Assistant turns keep the provider's raw content blocks and replay them unchanged.
  - Short timeout (8 s) and one retry by default: a live caller can't wait; the runtime falls back or escalates instead.
- **Scripted provider** (`providers/llm/scripted.py`) for deterministic tests without network, keys or cost.
- **Conversation state** (`runtime/state.py`): intent, detected intents, customer, collected details ("slots"), required/missing details, pending confirmation, verification, escalation, recent actions, counters. The model reports what it learned through a bounded `update_state` tool (max 15 details per update, 300 characters each, safe names only); code computes what is missing. A caller asking for a person sets escalation to *requested*.
- **Prompt assembly** (`runtime/prompts.py`), ordered by authority: (1) platform security and speaking-style policy, fixed in code; (2) agent policy from the published version (persona, purpose, tone, business rules, forbidden topics, escalation; business-supplied extra instructions are labelled as unable to override the rules); (3) business facts (name, hours, address) marked cacheable; (4) the call state and local time, which change every turn. "Open right now" is computed in code in the business's time zone, not guessed by the model. External content is wrapped by `wrap_untrusted()` with angle brackets escaped, so a document cannot close the wrapper and inject instructions.
- Verified: 150 tests (request shape: effort, no temperature, auto tool choice, cache markers, fallback, single-message tool results; tool-call and refusal mapping; timeout/429/529 to "unavailable", 400 to "request error"; missing tier mapping; scripted provider; prompt layer order and cache stability across turns; injection wrapper; open/closed by time zone; bounded state updates; escalation request; legacy temperature), ruff, mypy --strict. An opt-in live test (`uv run pytest -m live_llm`) runs once `ANTHROPIC_API_KEY` is set in `.env`; it is skipped today because no key is configured.

## Phase 2.3 — Secure tool framework
- **Tool definitions** (`tools/base.py`): each tool declares a name, a model-facing description, Pydantic input and output models, the permission scopes it needs, its side effect (`none` / `reversible` / `irreversible`), whether it needs the caller's confirmation or a verified caller, a timeout, retries, a per-call limit, an optional rule check, and an optional owning organization. Unsafe definitions are rejected at startup: tools with side effects can't auto-retry, and irreversible tools must require confirmation.
- **Registry and toolsets** (`tools/registry.py`): the model only sees tools that exist, that the tenant may use, and that the agent version grants. The list is sorted so it stays identical across turns (prompt caching). Granted tools that aren't available (not built yet, or another tenant's) are reported so publishing can flag them.
- **Tool Gateway** (`tools/gateway.py`), the only way a tool runs. Every request passes, in order: lookup → argument validation (extra fields such as a smuggled `tenant_id` are rejected) → tenant check → agent permission (the tool *and* every required scope must be granted; read never implies write) → business rules (verified caller, the tool's own rule, confirmation) → per-call rate limit → execution (timeout; retries only for read-only tools; an idempotency key for anything with side effects, so a retry can't double-book) → output validation (size-capped, wrapped as untrusted data) → audit record.
- **Confirmation** (`runtime/confirmation.py`): a confirmation-gated tool first returns "read this back and ask"; it only runs when the *same* tool with the *same* details is requested on a *later* caller turn and the caller's reply was a clear yes. The yes is detected by plain rules, not by the model, and anything hedged ("yes, actually wait", "not sure") is not a yes.
- **Safe failures:** expected failures ("no tables at 7") return a code and a hint the agent can act on; crashes, timeouts and bad output return a generic "that system is having trouble, offer a person". Internal error text never reaches the model or the caller.
- **Audit:** one record per tool request (including every refusal), with personal fields (phone, email, name, address, card, policy…) redacted. Today it goes to structured logs; a database table follows when calls are stored in Phase 3.
- **Built-in tools** (`tools/builtin.py`): `update_state` (always available; records what the caller said), `get_hours` (computed from configuration, never guessed), `transfer_to_human` (records the escalation with a reason and summary; falls back to taking a message when no transfer number is set; the actual phone transfer comes in Phase 3), `take_message` (needs the `messages:create` scope and the caller's confirmation of name and callback number).
- **Not yet:** the restaurant tools listed in the restaurant template (availability, create/cancel reservation, menu, confirmation SMS) need a reservations store and are built with the integrations; until then they show as unavailable and the model never sees them.
- Verified: 182 tests (unknown tool; not granted; read-scope can't write; another tenant's tool; invalid and extra arguments never execute; rule check; verification; full confirmation sequence including same-turn retry, hesitant reply and changed details; yes/no detection; idempotency key; no retry for side effects; timeout with retry for read-only; crash text never leaked; expected failure hint; invalid output; per-call limit; injected text stays inside data; audit redaction and denial records; built-in tools; toolset filtering), ruff, mypy --strict.

## Phase 2.4 — Agent runtime (the call loop)
- **CallSession** (`runtime/session.py`): runs one call, pinned to one agent version, and knows nothing about phones: the LiveKit worker (Phase 3), the text console and the tests all feed it caller text and speak what it returns.
  - **Greeting:** AI disclosure, then the recording notice (if set), then the greeting. The greeting is kept in the call state so the conversation sent to the model always starts with the caller.
  - **Each caller turn:** count the turn → classify a plain yes/no → ask the model with the layered prompt, current state and allowed tools → run any requested tools through the Tool Gateway (one at a time, since tools can change call state) → ask again with all results in one message → repeat at most `max_tool_iterations_per_turn` times → clean the reply for speech → decide whether to keep listening, transfer or end.
  - **Failures always end in something sensible to say:** if the model is unavailable it retries on a lighter tier (deep → balanced → fast); if all fail, or the tool loop hits its limit, the agent apologises and offers a person or a message; two failures in a row trigger a transfer (when the agent's escalation settings include "repeated failure"). A refused request gets a polite "I can't help with that". A refused or broken tool never crashes the turn.
  - **Escalation:** when the caller asks for a person (recorded by `update_state` or `transfer_to_human`) and a transfer number is set, the turn returns a *transfer* action with a **handoff**: reason, a one-line summary, collected details, customer info and actions already tried, so the caller doesn't repeat themselves. Without a transfer number it keeps going and takes a message instead.
  - **Limits:** silence re-prompts ("Are you still there?") then a polite goodbye; a maximum call length ends the call politely without another model request; conversation history is trimmed to the most recent 30 messages without splitting a tool request from its result (the call state keeps the older details).
  - **Per-turn metrics:** model calls and latency, tool calls and latency, total time, and token usage (including cached tokens), plus an event list that will feed the call inspector's timeline.
- **Speech guard** (`runtime/speech.py`): strips markdown, bullets, HTML-like tags and raw links, and caps replies at about 420 characters, cut at a sentence end.
- **Text console** (`runtime/console.py`): `uv run python -m voice_platform.runtime.console --template restaurant_receptionist --business "Joe's Diner" --timezone Asia/Kolkata --debug` lets you talk to an agent by typing, with the real model (needs `ANTHROPIC_API_KEY` in `.env`). An empty line simulates silence; `--debug` shows timings, tools and tokens.
- Verified: 203 tests, all with a scripted model (no network, keys or cost): greeting and first-message order; tool loop with both results in one message; known details reaching the next prompt; a message saved only after the caller's "yes please" on the next turn, and not after "yes, actually wait"; tier fallback; total outage → apology → transfer with handoff; refusal; tool-loop limit; unknown tool; caller asks for a person → transfer with details; no transfer number → no transfer; silence; call time limit; speech guard; history trimming; configured tier/effort/tools. Plus ruff and mypy --strict.

**Phase 2 (agent runtime) is complete.** Still to come with Phase 3: speech (STT/TTS), the LiveKit worker that drives `CallSession` from real audio, phone transfers, and storing calls, transcripts and tool audit records.

## Phase 3.1 — Local LiveKit, telephony port, test-call tokens, call storage
- **Local LiveKit server** in `compose.yaml` (`livekit/livekit-server:v1.13.11`, dev mode), bound to 127.0.0.1 only: 7880 (API/signalling), 7881/tcp and 7882/udp (WebRTC). It uses LiveKit's public development keys; settings refuse to start staging/production with the dev key or a secret shorter than 32 characters. `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` in `.env` switch to LiveKit Cloud without code changes.
- **TelephonyProvider port** (`telephony/ports.py`) and **LiveKitProvider** (`providers/telephony/livekit_provider.py`, `livekit-api` 2.0.1, APIs checked against the LiveKit docs on 2026-11-26). Today it issues browser join credentials and checks the server is reachable; phone numbers, SIP and transfers are added to the same port in 3.3/3.4. No LiveKit types leave the adapter.
- **Browser test calls:** `POST /api/v1/agents/{id}/test-calls` (needs `agents.write`; defaults to the newest version, or pass `version_id`) creates a call record and returns a 10-minute token for a fresh room named `call-<id>` (no names or numbers in room names, since LiveKit logs them). The token tells LiveKit to start the `voice-agent` worker for that room with dispatch metadata holding **ids only** (call, organization, agent version); it is signed, so only our server can choose which agent version a room runs.
- **Call storage** (migration `0005_calls`, row-level security on all tables): `calls` (direction, channel, status, numbers, intent, outcome, end reason, turns, token usage, timestamps), `call_messages` (transcript), `call_events` (timeline for the inspector), `tool_executions` (the tool audit trail, previously only in logs), `caller_messages` (messages taken by the agent; one per idempotency key, so a retry can't save it twice). Transcript, timeline and audit rows are insert-only for the app.
- **Worker side** (`calls/service.py`, `calls/recorder.py`): `load_call()` turns dispatch metadata into the call and its pinned agent version, re-checking every id inside the organization's context, and only for a call that hasn't started yet. `CallRecorder` writes turns, timeline events, token usage, tool audit records and caller messages, and marks the call started and ended. A recording failure is logged and never interrupts the call.
- **Calls API:** `GET /api/v1/calls` (paginated, filter by agent) and `GET /api/v1/calls/{id}` with timeline, tool audit and tokens. The transcript is included only with `calls.transcript.read` (Viewers see the call but not what was said).
- Verified: 209 tests (no version → 409; token checked with LiveKit's own verifier: room, agent dispatch, ids-only metadata; recorder → inspector round trip with transcript, timeline, tools, tokens, duration; a call loads only once; forged organization or version finds nothing; Viewer gets no transcript and can't start test calls; the local LiveKit server answers with the configured keys), ruff, mypy --strict.
- **Next (3.2):** the agent worker that joins these rooms, turns speech into text, runs `CallSession`, and speaks the reply. It needs `ANTHROPIC_API_KEY`, a speech-to-text key (Deepgram) and a text-to-speech key (Cartesia) in `.env`.
